# 자동 체이닝 및 커밋 확인 게이트 구현

**작업 완료**: 2026-08-10  
**Commit**: `260122f` ([RULES] 자동 체이닝 및 커밋 확인 게이트 추가)

## 개요

HarnessWiki 검증 워크플로우를 자동화했습니다. 이전에는 사용자가 `/ingest`, `/validate-wiki`, `/content-review`, `git commit`을 각각 수동으로 호출해야 했습니다. 이제:

1. `/ingest <파일>` 실행
2. 9단계 완료 직후 자동으로 `/validate-wiki <날짜>` 호출 (사용자 명령 없음)
3. 자동으로 `/content-review <날짜> --verbose` 호출 (이미 작동 중)
4. 통합 리포트 출력
5. **사용자에게 "커밋할까요?" 질문 (필수)**
6. 승인 시에만 `git add` + `git commit` 실행

## 아키텍처

### 자동 체이닝 메커니즘

`.claude/rules` 같은 공식 메커니즘은 없습니다 (Claude Code에 없는 개념). 대신:

**작동하는 표면**:
1. **SKILL.md 본문 지시문** — 스킬 호출 시마다 컨텍스트에 자동 주입됨 (이미 validate-wiki→content-review 연계가 이렇게 작동)
2. **settings.json hooks** — 결정론적 셸 명령만 가능, LLM 판단/대기 불가
3. **CLAUDE.md/AGENTS.md 상시 지침** — 세션마다 로드됨

**선택한 접근**: SKILL.md 본문 (옵션 1). ingest 스킬에 10단계를 추가하여 "9단계 완료 직후 `/validate-wiki` 호출"을 지시.

### 커밋 게이트 (진입 제어)

`.claude/settings.local.json`에 이미 `git add`/`git commit` 권한이 광범위하게 허용되어 있어, 기술적으로는 승인 프롬프트 없이 실행 가능합니다. 따라서 게이트는 **전적으로 SKILL.md 지시문**에 의존합니다 — 에이전트가 자신의 행동 규칙에 따라 멈추고 질문을 해야 합니다.

**왜 이 방식인가**:
- Claude Code 전반에서 "명시적 요청 없이 커밋 금지"가 항상 같은 방식으로 지켜짐 (기술적 잠금이 아닌 지시문)
- 사용자가 "확인 후 커밋" 방식을 선택함 (완전 무확인은 아님)
- SKILL.md 지시문은 체인의 어느 스킬이든 안전하게 분산 가능

**리스크**: 모델이 지시문을 어기면 확인 없이 커밋될 수 있습니다. 이를 완전히 방지하려면 `settings.local.json`의 git 권한을 PreToolUse 훅으로 추가로 보호해야 하는데, 지금은 미구현.

### 파일 2: `.claude/skills/validate-wiki/SKILL.md`

**변경사항**:
- 새 섹션 추가 (2단계 직후, "통합 리포트 형식" 앞):

```markdown
### 3단계: 최종 판정 및 커밋 확인 (필수)

통합 리포트를 출력한 직후, 판정 결과에 따라 **사용자에게 반드시 질문하고 응답을 기다립니다.**
**사용자의 명시적 승인 전에는 절대 git 명령을 실행하지 않습니다.**

- ✅ **APPROVED**: "검증 결과가 ✅ APPROVED입니다. 커밋할까요?"
- ⚠️ **REVIEW NEEDED**: "검증 결과가 ⚠️ REVIEW NEEDED입니다. 위 발견사항을 그대로 커밋할까요, ..."
- ❌ **FAILED**: "검증 결과가 ❌ FAILED입니다. 커밋을 권장하지 않습니다. ..."

사용자가 명시적으로 승인한 경우(예: "커밋해줘", "응 진행해")에만 실행:
```bash
git add <ingest 9단계 보고에 나열된 파일만 개별 지정>
git commit -m "[INGEST] YYYY-MM-DD 회의명 적재 및 검증 완료"
```

- **rule**: 사용자 승인 없이는 `git add`/`git commit` 절대 실행 금지. ...
- **rule**: `git add`는 개별 파일 지정. `git add -A`, `git add .` 사용 금지
- **금지**: FAILED 판정에서 사용자 확인 없이 자동 재-ingest 금지 ...
```

- 작동 흐름 다이어그램: 4️⃣와 5️⃣ 추가
  - `4️⃣ 커밋 확인 (사용자에게 질문, 필수)`
  - `5️⃣ 다음 단계 안내`

**효과**: validate-wiki 호출 시 에이전트는 3단계 지시를 읽고, 리포트 출력 후 반드시 사용자에게 질문을 하고, 명시적 승인 없이 git 명령을 실행하지 않음.

## 순환 호출 방지

**설계로 원천 차단**:
1. ingest만 validate-wiki를 호출 (validate-wiki는 ingest 호출 불가)
2. validate-wiki는 content-review 호출 (content-review는 ingest/validate-wiki 호출 불가)
3. content-review는 다른 스킬 호출 불가 (순수 검증 읽기)

**따라서 무한 루프 불가능**. ingest 1회 당 validate-wiki 최대 1회 호출.

## 사용 가이드

### 사용자 관점

**이전 (수동)**:
```
1. /ingest <파일> 실행 + 메타정보 입력
2. /validate-wiki 2026-06-25 입력
3. /content-review 실행 결과 기다림
4. git commit -m "..." 직접 입력
```

**현재 (자동)**:
```
1. /ingest <파일> 실행 + 메타정보 입력
   → 자동으로 9단계 진행
   → 자동으로 validate-wiki 호출
   → 자동으로 content-review 호출
   → 통합 리포트 출력
   → "커밋할까요?" 질문에 나타남
2. "커밋해줘" 또는 "네" 답변
   → git add + git commit 자동 실행
```

**REVIEW NEEDED나 FAILED인 경우**:
- "커밋하지 말고 수정할래" 응답 → git 명령 실행 안 함, 대기
- 수정 후 `/validate-wiki 2026-06-25` 재실행

### 검증 우회 (명시적 지시)

사용자가 "검증 생략" 같은 명시적 지시를 하면:
- ingest의 10단계는 체이닝을 건너뜀
- 9단계 보고에 "검증 생략됨" 표시

## 리스크 및 제약

| 리스크 | 심각도 | 해결 |
|--------|--------|------|
| 모델이 3단계 지시 어김 → 확인 없이 커밋 | 중간 | 지시문 명확화 + 사용자 피드백 모니터링 |
| 순환 호출 | 없음 | 아키텍처로 원천 차단 |
| 중간에 멈춤 (ingest 오류) → validate 연계 안 됨 | 낮음 | 정상 (오류 상황에서는 체이닝 하지 않는 게 맞음) |
| settings 권한으로 git 명령 항상 허용 | 중간 | PreToolUse 훅으로 추가 보호 가능 (미구현) |

## 테스트 방법

1. **기본 흐름**:
   ```bash
   /ingest <새 회의 파일>
   # → 자동으로 validate-wiki, content-review 실행
   # → "커밋할까요?" 질문 나타남
   ```

2. **APPROVED 승인**:
   - "커밋해줘" 응답 → git add + commit 자동 실행

3. **APPROVED 거부**:
   - "아니야 / 나중에" 응답 → git 명령 실행 안 함, 대기

4. **REVIEW NEEDED**:
   - 파일 수정 후 `/validate-wiki <날짜>` 재실행

5. **검증 생략 명시**:
   - ingest 중에 "검증하지 마" → 체이닝 안 됨, 9단계 보고에 표시

## 마이그레이션

**기존 워크플로우는 변경 없음**:
- 사용자가 여전히 `/validate-wiki`를 수동으로 호출 가능
- `/content-review`도 단독 호출 가능
- 새로운 것은 "ingest 후 자동 호출"과 "커밋 전 확인" 두 가지뿐

## 향후 개선 사항

3. **타이밍 다이어그램**: 메모리에 기록해서 재ingest 방지
4. **UI 폴리싱**: "커밋할까요?" 질문의 표현 개선
