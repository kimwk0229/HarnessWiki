# 엣지 케이스 및 판단 기준

ingest 중에 만날 수 있는 애매한 상황들과 해결 방법.

## 1. 주제 매칭: 관련인지 판단하기

### 판단 기준

**관련** (주제 페이지 갱신):
- 회의에서 직접 다룬 주제
- 의사결정이나 액션이 발생한 주제
- 상태 업데이트가 필요한 주제

예시:
```
회의 내용: "결제 연동 개발 진행: API 개발 중, 8월 중순 완료 예정"
→ 결제-연동 토픽에 추가 (O)
```

**검토 필요** (판단 후 추가):
- 회의에서 부분적으로 언급된 주제
- 관련성이 간접적인 주제

예시:
```
회의 내용: "결제 연동 완료되면 정산 자동화도 함께 진행하자"
→ 정산-주기 토픽: 결정사항으로 추가 (O) or 참고 수준 (판단 필요)
→ 기준: 실제 진행 중인지, 아니면 계획 수준인지?
   진행 중 → 추가, 계획 수준 → 추가 안 함
```

**관련 없음** (무시):
- 배경 설명 수준의 언급
- 과거 작업 회상
- 일반적인 정보

예시:
```
회의 내용: "작년 온보딩 개선 프로젝트 때 배운 점들이..."
→ 온보딩-개선 토픽: 과거 정보이므로 추가 안 함 (O)

회의 내용: "Q3에 대시보드 개편 계획도 있어"
→ 대시보드-개편 토픽: Q3 계획 수준이므로 "예정" 수준으로만 추가 (O)
```

### 판단 불가능할 때

판단 불가능하면 **관련성 있다고 가정**하고 추가합니다.
나중에 정산 단계(Lint)에서 고아 항목을 감지하고 정리할 수 있습니다.

## 2. 모순 처리: 이전 내용과 충돌할 때

### 시나리오 1: 상태 변경

**상황**: 이전 페이지에는 "X는 Y다"라고 했는데, 새 회의에서 "X는 Z로 변경"

**처리 방법**: 변경이력으로 기록

```markdown
## 결정사항

### 2026-08-10 (최신)
- X 담당 변경: 이전 강태우 → 현재 박준서 ([2026-08-10 회의 링크])

### 2026-07-23
- X 담당: 강태우
```

### 시나리오 2: 완료 상태 변경

**상황**: 이전에 "진행 중"이었는데, 새 회의에서 "완료"

**처리 방법**: 현황 섹션 갱신, 결정사항은 신규 블록 추가

```markdown
## 현황

2026-08-10 기준:
- 상태: 완료 ✅
- 완료일: 2026-08-10

## 결정사항

### 2026-08-10 (최신)
- 온보딩 개선 프로젝트 완료 (42% → 27% 개선율)
출처: [2026-08-10 회의 링크]
```

### 시나리오 3: 일정 변경

**상황**: 이전에 "5월 말 완료"였는데, 새 회의에서 "8월 중순으로 연기"

**처리 방법**: 일정을 현황에 갱신, 변경 이유는 결정사항에 기록

```markdown
## 현황

2026-08-10 기준:
- 목표 완료: 2026-08-15 (이전 2026-05-31)

## 결정사항

### 2026-08-10 (최신)
- 목표 완료일 변경: 2026-05-31 → 2026-08-15 (테스트 계정 이슈로 인한 재연기)
출처: [2026-08-10 회의 링크]

### 2026-06-11
- 목표 완료일: 2026-05-31 (테스트 계정 인증 오류로 재검토 중)
```

### 시나리오 4: 실제 모순 (정보 오류)

**상황**: 이전에 "A는 X다"라고 했는데, 새 회의에서 실제로는 "A는 Y다" (오류 발견)

**처리 방법**: 최신 블록에 정정 내용 기록, 과거 블록은 유지 (감사추적)

```markdown
## 결정사항

### 2026-08-10 (최신)
- A의 실제 값: Y (이전 X는 오류, 원인: [설명])
출처: [2026-08-10 회의 링크]

### 2026-07-23
- A의 값: X (당시 정보)
```

## 3. 신규 토픽 생성: 언제 필요한가?

### 생성 조건

신규 토픽을 생성할 때:

1. **회의에서 직접 다룬 새로운 주제**
   ```
   회의 내용: "새로운 모바일 앱 프로젝트 시작하기로 결정"
   → 기존 토픽 없음 (모바일-앱 없음)
   → 신규 토픽 생성: wiki/topics/모바일-앱/모바일-앱.md (O)
   ```

2. **여러 회의에서 반복되는 주제**
   ```
   2026-06-11: "고객사별 정산 주기가 다름"
   2026-07-09: "고객사B 주 1회 요청"
   → 정산 관련 토픽 필요
   → 기존 토픽 "정산-주기" 있으면 갱신
   → 없으면 신규 생성: wiki/topics/정산-주기/정산-주기.md (O)
   ```

### 생성 제외 조건

신규 토픽을 생성하지 않을 때:

1. **일회성 이슈**
   ```
   회의 내용: "이번 회의 진행 방식이 너무 길었다"
   → 프로젝트 정보 아님, 토픽 불필요 (X)
   ```

2. **다른 토픽 내 항목으로 충분**
   ```
   회의 내용: "결제 수단 추가로 신용카드/은행이체 둘 다 지원"
   → 결제-연동 토픽의 "결정사항" 섹션에 추가 (O)
   → 신규 토픽 "신용카드-연동" 불필요 (X)
   ```

3. **뚜렷한 경계가 없는 주제**
   ```
   회의 내용: "QA 프로세스 개선 필요"
   → 뚜렷한 프로젝트나 일정 없음
   → 토픽 생성 보류, 추후 구체화 필요 (판단 연기)
   ```

### 신규 토픽 생성 시 절차

1. 슬러그 결정: `kebab-case` 한글
   ```
   "모바일 앱 프로젝트" → "모바일-앱"
   ```

2. 폴더 생성: `wiki/topics/슬러그/`

3. 페이지 생성: `wiki/topics/슬러그/슬러그.md`
   - frontmatter (updated 필드)
   - 기본 섹션 (현황, 결정사항, 관련 페이지 등)

4. **반드시** `index.md`에 등록

5. 링크 검증 (모든 링크가 유효한지)

## 4. 링크 경로 오류: 언제 발생하는가?

### 오류 1: 깊이 혼용

**상황**:
```markdown
같은 토픽 페이지에서:
- 한 링크: `../../../raw/2026-08-10_회의/meta.md` (O, 3단계)
- 다른 링크: `../../raw/2026-08-10_회의/meta.md` (X, 2단계)
```

**원인**: 깊이 계산 실수

**검증**: `scripts/check_links.py`로 자동 감지

```bash
python scripts/check_links.py D:\HarnessWiki\wiki
# 출력: 깊이 불일치 경고, 유효하지 않은 경로 목록
```

### 오류 2: 롤업에서의 링크

**상황**:
```markdown
decisions.md에서:
- 토픽 링크: `../topics/슬러그/슬러그.md` (O)
- 토픽 링크: `../../topics/슬러그/슬러그.md` (X, 너무 깊음)
```

**기준점**: rollup 페이지의 위치
- decisions.md: `wiki/decisions/` → 토픽은 `../topics/`
- action-items.md: `wiki/action-items/` → raw는 `../../raw/`

### 검증 방법

모든 링크는 ingest 완료 전에 검증:

```bash
python scripts/check_links.py <wiki-path> --strict
```

**--strict 플래그**:
- 깨진 링크 (존재하지 않는 파일)
- 깊이 불일치 (3단계 raw가 2단계로 되어 있는 경우)
- 형식 오류 (상대경로가 절대경로로 되어 있는 경우)

## 5. 액션아이템 상태 관리

### 완료된 액션아이템

**상황**: 이전 회의의 액션이 현재 회의에서 완료됨

**처리**:
```markdown
## 2026-08-10 제품 주간회의

- [x] 최민아: A/B 테스트 결과 정리 — 완료 (2026-08-10)
출처: [2026-07-23 회의](../../raw/2026-07-23_제품주간회의/meta.md)
```

체크박스: `[ ]` → `[x]`

### 오래된 미완료 액션

**상황**: 4주 이상 미완료인 액션

**처리** (ingest 중 아님, Lint 단계):
- action-items.md에서 플래그
- 담당자에게 현황 확인

### 액션 재할당

**상황**: 원래 담당자가 바뀜

**처리**:
```markdown
- [ ] 박준서 (이전: 강태우): 결제 API 개발 (8월 15일)
```

명확히 표기 (과거 담당자도 기록)

## 6. 참석자 불명확할 때

### 상황

회의 메모에 참석자 목록이 없거나 불완전한 경우

### 처리

사용자에게 확인:
```
회의 참석자를 확인해주세요:
- 필수: 적어도 2-3명
- 선택: 없으면 생략 가능
- 형식: 이름1, 이름2, 이름3
```

불확실하면 **"[불명확]" 또는 생략** 가능

### meta.md 작성

```yaml
participants:
  - 박준서
  - 강태우
  # - [기타 불명확]
```

## 7. 자료유형 판단

### "manual" (수동 메모)

특징:
- 체계적인 bullet points
- 정갈한 문장
- 명확한 섹션 구분

예:
```
## 결제 연동 진행상황
- API 개발 중
- 테스트 계획: [계획]
- 완료 목표: 8월 15일
```

### "stt" (STT 전사)

특징:
- 마크 (`[00:05]`, `Speaker:`)
- 비유창함 (`어~ 그런데`, `그래서 뭐...`)
- 말투 특성 (반복, 자족사 등)

예:
```
[00:05] Speaker: 어~ 그래서 결제 연동 진행상황인데, 
우리가 지난번에 API 개발을 시작했고, 이제 뭐... 테스트를 하고 있어.
완료는 8월 15일 정도로 목표를 잡았어.
```

### "hybrid" (혼합)

특징:
- 일부는 정갈한 메모
- 일부는 전사 마크나 비유창함

예:
```
## 결제 연동
[00:05] 박준서: API 개발 중입니다. 어~ 그런데 테스트 계정 이슈가 있어서...

### 결정사항
- API 개발 목표: 8월 15일
- 테스트 계정: [조사 중]
```

### 판단 불가능

불확실하면 **사용자에게 확인**:
```
자료유형을 선택해주세요:
1. manual (수동 메모, 정갈함)
2. stt (STT 전사, 구어)
3. hybrid (혼합)
```

## 8. 중복 회의 처리

### 같은 날 다른 회의

**상황**: 2026-08-10에 "제품 주간회의"와 "긴급 회의" 2개

**처리**:
```
raw/2026-08-10_제품주간회의/
raw/2026-08-10_긴급회의/
```

슬러그로 구분

### 이전에 입수되지 않은 회의

**상황**: 지난주 회의가 이번에 들어옴

**처리**: 날짜 기준으로 역사 순서대로 ingest
- 이전부터 일관성 있게 (새 회의부터 하지 말 것)
- 주제 페이지도 시간 순서대로 갱신

## 9. 신규 토픽 vs 기존 토픽 병합

### 상황

유사한 주제가 여러 슬러그로 존재할 수 있나?

### 규칙

**절대 불가능**. 같은 주제는 1개 슬러그만.

### 만약 발견되면

- Lint 단계에서 "중복 주제 페이지" 플래그
- 하나로 병합 (수동)

예시 방지:
```
결제-연동 O
payment-integration X
결제연동 X
```

## 10. log.md 기록 예시

```markdown
- [INGEST] 2026-08-10 제품 주간회의 적재 완료.
  생성: raw/2026-08-10_제품주간회의/.
  갱신: 결제-연동(완료 목표 8월 중순 확정), 정산-주기(재보류).
  decisions.md/action-items.md 동시 갱신.
  링크 검증 완료 (깨진 링크 0건).
```

간결하되 생성/갱신 파일 목록은 필수.
